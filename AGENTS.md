# rapply

Next.js 16.3 (App Router) + React 19 + Tailwind v4 + Prisma 7.10/Postgres personal-management app. **UI, comments, and API error strings are all French** (`lang="fr"` in `app/layout.tsx`).

## `PageLayout` (`app/components/PageLayout.tsx`)

Owns the fixed-header scaffolding for every page: `variant="standard" | "search" | "filters" | "responsive-tools"`, slots `leading/title/titleActions/actions/controls/subheader`, and a `refreshable` flag (see Pull-to-refresh below). Use it instead of hand-rolling header/offset CSS in new views.

`standalone` (default `false`) is for the two pages outside `(dashboard)` — see the `/parametres`/`/recettes` note under Page/component pattern.

## Commands

- pnpm is the package manager. A stale `package-lock.json` also exists — ignore it; `pnpm-lock.yaml` is the real lockfile and the only one the Dockerfile uses (`--frozen-lockfile`).
- `pnpm dev` / `pnpm build` / `pnpm start` / `pnpm lint`. **No test runner, no formatter, no `typecheck` script** — `pnpm build` is the only type check, and it is the only gate that actually passes. **`pnpm lint` fails at baseline** (81 errors / 4 warnings) and is not a regression gate: they are almost entirely `no-explicit-any` on the deliberate `any` entity types, plus `set-state-in-effect` in `BurgerMenu`/`login` and one `no-img-element`. Compare against that baseline instead of expecting zero. Bare `eslint` via flat config `eslint.config.mjs`.
- `npx prisma generate` — regenerate the client after editing `prisma/schema.prisma`. No npm script exists; run it directly.
- `npx prisma migrate dev` — schema migrations (`prisma/migrations/` exists, 4 applied). Config is `prisma7.config.ts` (Prisma 7's default filename), which is also where `migrations.seed` is declared — there is no `package.json` `prisma.seed` key.
- `pnpm seed` (`prisma db seed` → `tsx prisma/seed.ts`) and `pnpm create-user` (`tsx prisma/create-user.ts`). Both import the driver-adapter client from `app/lib/prisma.ts`; don't give them a separate client. The two files are **completely independent** — nothing imports `create-user.ts` — so changing one cannot break `pnpm seed`.

## Account CLI (`prisma/create-user.ts`)

Three subcommands, plus the no-argument form which defaults to `create`:

```
pnpm create-user                      # create, prompts for email + password
pnpm create-user create <email>
pnpm create-user password <email>     # also increments tokenVersion
pnpm create-user delete <email>       # aliases: user:password, user:delete
```

- **It only runs on the host, never in the container.** The runner stage of the `Dockerfile` copies `public`, `.next/standalone`, `.next/static` and `prisma/` but **no `node_modules` and no `package.json`**, and `tsx` is a devDependency — so `prisma/` being present in the image is misleading. The globally installed `prisma@6.8.2` is not a fallback either: it mismatches the pinned 7.10.0, and `datasource` has no `url` (it comes from `prisma7.config.ts`).
- Server prerequisites, in this order: `git pull`; write `DATABASE_URL` into a `.env` on the host **before** `npx prisma generate` (the config file loads the env at startup, so `generate` fails without it); `pnpm install`; `npx prisma generate`.
- **Password input is masked in raw mode, not via readline's `_writeToOutput`** — that private API changes behaviour between Node versions. Outside a TTY (pipe, file, `docker exec` without `-t`) masking is impossible, so it *says so* rather than pretending. A module-level `queue` holds characters received between questions: a pipe delivers every line in one chunk, and without it the confirmation would be swallowed after the first question.
- `password` **always** bumps `tokenVersion` (same mechanism as `app/api/auth/revoke`), because changing a password means the account was compromised. There is deliberately no `--no-revoke`; the secure default is the one you get.
- `create` refuses an existing email. An earlier version used `update: {}`, which reported `User créé` and changed nothing — not even the password.
- `delete` has **no `--yes`**: you must type the email in full. All 8 `user` relations are `onDelete: Cascade`, so deleting a user silently destroys reminders, notes, transactions, categories, budgets, schedule events, recipes and push subscriptions, and there is no import endpoint. It lists the child row counts and points at `GET /api/export` first.
- Passwords are capped at **72 bytes**, not 72 characters: bcrypt ignores everything beyond, so the stored hash would not match what was typed. An accented character is 2 bytes.


## Prisma 7 gotchas

- **Driver adapter is mandatory** (Prisma 7 has no query engine): `app/lib/prisma.ts` wires `PrismaPg` from `@prisma/adapter-pg` into `PrismaClient({ adapter })`. Never revert to the legacy `prisma-client-js` generator or drop the adapter.
- Client generates to `app/generated/prisma` (set in `prisma/schema.prisma`), is **gitignored**, and is imported **only** as `../generated/prisma/client` from `app/lib/prisma.ts`. Nothing else imports it.
- `datasource` in the schema has **no `url`** — it comes from `process.env.DATABASE_URL` via `prisma7.config.ts` (`import "dotenv/config"`).
- Don't use the Dockerfile's global `prisma@6.8.2` as a reference; the project pins `7.10.0`.

## Auth & request pipeline

- Auth is verified in **`proxy.ts` at the repo root** (Next 16 renamed `middleware` → `proxy`; it must not live in `app/`, and there is no `app/middleware.ts`). It exports `proxy`, runs in the Node runtime, verifies the httpOnly `token` JWT (`JWT_SECRET`), then injects `x-user-id`.
- Route handlers do **not** re-parse cookies. They call `getUserId(req)` from `app/lib/auth.ts` and must scope every Prisma query by that id. `getUserId` **throws** `UNAUTHENTICATED` rather than returning 401 (practically unreachable — the proxy 401s first).
- The proxy runs a `prisma.user.findUnique` **on every single request** to compare `tokenVersion` (session revocation, bumped by `app/api/auth/revoke/route.ts`). Don't add more DB work there.
- The proxy also enforces **CSRF**: for `POST/PUT/PATCH/DELETE` under `/api/*` it compares `origin` (or `referer`) host to `x-forwarded-host`/`host`, and returns 403 on mismatch. It *allows* the request when both headers are absent — so this is origin-based, not a token.
- Unauthenticated, by design: `/login`, `/api/auth/login`, `/api/push/send`, `/api/push/digest`, and static assets (matcher at `proxy.ts:90`). The two push routes use `Bearer ${CRON_SECRET}`, not the proxy. `app/api/auth/logout` also has no auth. `/api/export` and `/api/push/test` **are** authenticated (`getUserId`) — that's the only gate on `/api/push/test`, there's no `NODE_ENV` check, so the "Tester la notification" button in `PushSubscribeButton` is shown in every environment, not just dev.
- Login cookie gotcha: in `app/api/auth/login/route.ts` the `token` cookie's `secure` flag is derived from `x-forwarded-proto`/`req.nextUrl.protocol`, **not** `NODE_ENV`. Behind an HTTPS proxy (Traefik/ngrok) `NODE_ENV` is still `production`/`development` inconsistently; an `NODE_ENV`-based flag makes the browser drop the cookie and the user stays stuck on `/login`.
- Login rate limiting (`app/lib/rate-limit.ts`) is an **in-memory `Map`** — lost on restart, per-process. 5 failures / IP / 15 min ⇒ 15 min block. Resolves the client IP via `cf-connecting-ip` → `x-forwarded-for` → `x-real-ip`.

## Page / component pattern

- `app/(dashboard)/**/page.tsx` are **async server components** that `Promise.all` their data via `serverFetch` and pass plain props to a `"use client"` view in `app/components/`. Canonical: `app/(dashboard)/reminders/page.tsx`.
- `app/lib/server-fetch.ts` forwards the `token` cookie with `cache: "no-store"` and calls the **absolute** `NEXT_PUBLIC_APP_URL` — i.e. every SSR render makes a real HTTP round-trip to your own server. That URL must be correct *and reachable from the container*. It **throws** on non-2xx; only `app/(dashboard)/page.tsx` (`safe<T>()`) and the two pages outside the group add fallbacks.
- Client views hold entity state locally (`useState(initial)`, entity types are `any`, no shared DTOs, no react-query/SWR) and call `fetch("/api/...")` directly. After a mutation they **lift the result into local state** via an `onSaved(updated, deletedId, added)` callback — no `router.refresh()`, no `revalidatePath`. (That is the norm, not the law: `ScheduleView` events and the `SettingsView` currency both call `router.refresh()`, because neither keeps a local mirror of its entities.)
- Modals live in the same file as their view and use the `.pwa-sheet-overlay` + `.pwa-sheet` pair. They close on overlay click and on `✕` — **no Escape handler exists in any of the six edit modals**, only `DashboardBudgets.tsx` has one. In installed-PWA mode (`@media (display-mode: standalone)`), the safe-area-bottom padding lives on `.pwa-sheet` itself, not on `.pwa-sheet-overlay`: the overlay is `flex items-end` on mobile and carries `bg-black/60`, so giving *it* the padding pushed the sheet up and exposed a full-width strip of the overlay's own dark background underneath — read as a solid black bar under every sheet, not just one view's.
- The `alive` unmount guard (`const alive = useRef(true)` + cleanup-`useEffect`, wrapping the `setSaving(false)` / `setDeleting(false)` in each `finally`) is **optional and easy to get wrong**: if you write it, the setup body must set `alive.current = true`, because React StrictMode is on by default with the App Router (`next.config.ts` never sets `reactStrictMode`) and the dev double-invoke leaves the flag `false` after mount — every guard then silently skips, and the save button stays stuck on its spinner. It was exactly this bug in 6 of the 7 views before the fix. Note the guard is largely redundant anyway: React 18+ removed the setState-after-unmount warning, so the call is already a silent no-op. Prefer aborting the `fetch` if you need real cancellation.
- **Derived numbers are computed server-side, never re-derived in a view.** `/api/budgets` returns a `spent` field per budget (Prisma `aggregate` over `_sum.amount`, scoped by the period and by `categoryId` when set, otherwise `type: "EXPENSE"`); `spentFor` in `app/api/budgets/route.ts` is the single implementation, exported so `budgets/[id]/route.ts` can reuse it. GET, POST and PUT all include `spent`, because the POST/PUT responses feed `onSaved` straight into the list — omitting it would render a freshly saved budget at 0. Two hand-rolled client copies of that aggregation used to exist and were removed. `BudgetsView` therefore takes no `transactions` prop: a prop captured at SSR is frozen, so any figure derived from it silently goes stale against a budget the user just edited.
- `app/parametres/page.tsx` and `app/recettes/page.tsx` are **outside** the `(dashboard)` group, so they get no `MobileHeader`, no `<aside>` sidebar, no bottom nav, and no `ServiceWorkerRegistrar`. Their views (`SettingsView`, `RecipesView`) mount `<PageLayout standalone>`: `standalone` zeroes out `--mobile-header-height`/`--page-sidebar-width` (down to `env(safe-area-inset-top)` / `0px`) so the header doesn't reserve space for chrome that isn't there. Don't drop `standalone` without re-adding an equivalent offset, and don't add a per-variant padding override instead — overwrite the two CSS vars at the root, which every consuming rule already inherits.
- **Pull-to-refresh** (`app/components/PullToRefresh.tsx`, mounted by `PageLayout`) makes `PageLayout` a **client component** — it was a server one. The wrapper covers `children` **only**, and that is load-bearing: a `transform` on an ancestor turns any `position: fixed` descendant into containing-block-relative, so translating the root would drag `.mobile-page-header` (fixed, z-40) down while `MobileHeader` (fixed, z-50, rendered *outside* `PageLayout` in the group layout) stayed put. The indicator is a **sibling** of the wrapper for the same reason.
- The same containing-block rule bit the **add/edit modals**, which *are* inside `children` (every view renders its `.pwa-sheet-overlay` alongside its list). `paint()`/`settle()` must leave the wrapper's inline `transform` fully **empty** (`""`) once idle, never `translate3d(0,0,0)` — that string is still a non-`none` transform and keeps the wrapper as a containing block, so any modal opened afterward sizes itself to the page's content height instead of the viewport (invisible on a short page, sheet pinned far below the fold on a long one). This triggers from any vertical touch-drag starting at `scrollY === 0`, which is most taps near the top of a page, so it reproduced on effectively every "add" button.
- `settle()` only runs the `translate3d(0,0,0)` → animate-back-to-`""` dance when `offsetRef.current > 0` (an actual pull happened). A plain tap that passes the start guards but never drags (e.g. tapping a list/grid row to open its detail modal — a reminder row, a recipe card) still fires `onTouchEnd → settle()`; writing the non-empty transform unconditionally there reopened the exact bug above for ~200ms on *any* tap at `scrollY === 0`, not just the header. Recipes reproduced it reliably because `handleSaved` prepends new recipes to the top of the list, so the card you just created sits at `scrollY === 0` right when you tap it.
- The gesture writes the pixel distance straight to `wrapperRef.current.style.transform` in `touchmove` and keeps only a 4-state machine (`idle`/`pulling`/`armed`/`refreshing`) in React state. Never put the offset in state: `children` is the whole page, so every pixel would re-render all 7 views and their lists.
- `touchmove` is bound on `window` with `{ passive: false }`. React attaches `touchstart`/`touchmove` **passively at the root**, so `preventDefault()` inside an `onTouchMove` prop is silently ignored and the browser's own scroll/refresh wins.
- Four start guards, all needed: `window.scrollY > 0`; the target being inside a `.pwa-sheet-overlay`; the target being inside `.mobile-page-header` (the fixed header — a tap on "Ajouter" has enough finger jitter to clear `SLOP` and arm `paint()`/`settle()`, and the modal that then opens mounts while the wrapper's `transform` hasn't been cleared yet, visibly jumping once it is); and any ancestor with `overflow-y` `auto`/`scroll` **whose `scrollHeight` exceeds `clientHeight`**. Testing `scrollTop > 0` instead is a bug — a freshly opened modal has `scrollTop === 0`, so the page used to slide *behind* the sheet. `html { overscroll-behavior-y: contain }` suppresses Android's native pull-to-refresh, without which two indicators fire at once.
- It calls `location.reload()`, **not** `router.refresh()`: the views initialise with `useState(initial)` and never resync, so a refresh would hand them new props they ignore and the gesture would appear to do nothing. A 5 s `setTimeout` resets the view if the navigation never commits (offline).
- Opt out per page with `<PageLayout refreshable={false}>`; the default is `true` because all 8 pages are DB-backed. Measured on the dev server: SSR is 0.9–1.5 s per page (`/` 1.52 s, `/budgets` 1.44 s, `/notes` 0.99 s) and single endpoints 0.41–0.90 s (`/api/notes` 0.41 s, `/api/budgets` 0.90 s), so the indicator is genuinely visible and needs no artificial minimum.
- Every dashboard route plus `/recettes`/`/parametres` now has its **own** `loading.tsx` (`app/(dashboard)/reminders|notes|finances|budgets|schedule/loading.tsx`, `app/recettes/loading.tsx`, `app/parametres/loading.tsx`), each rendering the page's **real** `PageLayout` call (same `title`/`variant`/`standalone`/`leading`) with `Skeleton` (`app/components/Skeleton.tsx`) placeholders only for the data-dependent body/actions/controls. This is why the title, header icons, and (for `/recettes`) the back button and search input chrome appear instantly instead of behind a full-page spinner: Next.js's per-segment `loading.tsx` convention wraps only `page.tsx` in `Suspense`, not the surrounding `(dashboard)/layout.tsx` (which is why `MobileHeader`/sidebar/bottom nav were already instant before this), and since `PageLayout` needs no data to render its chrome, duplicating its *props* (not its logic) into each `loading.tsx` costs nothing and can't drift out of sync with the real header's offset math (no CSS to hand-tune — it's the same component). `app/(dashboard)/loading.tsx` is now specific to `/` (Tableau de bord) only, since every other dashboard segment has its own override; `app/loading.tsx` (root) now only backs `/login`, which has no server data fetch and barely shows it. New dashboard routes need their own `loading.tsx` mirroring their view's `PageLayout` props, or they'll silently fall back to the (wrong-shaped) `/` one.
- `ConnectionBubble` is mounted in **`app/layout.tsx`** (root, not the `(dashboard)` layout) so it also covers `/login`, `/recettes` and `/parametres`. It reads `navigator.onLine` through **`useSyncExternalStore`**, not `useState` + `useEffect`: `setOnline(navigator.onLine)` inside the effect body trips `set-state-in-effect` (this lint rule is on, it's what `BurgerMenu`/`login` already trip). The `getServerSnapshot` returns `"unknown"` and the component renders `null` for it, which both avoids a hydration mismatch and suppresses the green flash when the PWA cold-starts offline — no `mounted` flag needed.
- It is `pointer-events: none` **on purpose**: at `top-right` it still visually sits over the corner of the `actions` slot of `.mobile-page-header` ("Ajouter une note" on `/notes`, `/budgets`, `/finances`, `/recettes`), and this is the only thing keeping that button tappable underneath. Verified with `document.elementFromPoint` at the bubble's centre. Don't make it interactive, and don't raise its `z-index` above `.initial-loading` (100), which is meant to cover the whole screen. Kept deliberately small (`1rem`, a corner badge, not a same-size circle) so it no longer visually hides the add button's icon the way the original `1.75rem` size did — shrink `.connection-bubble`/`__dot`/`__slash` together if you resize it again, they're hand-tuned to the same ratio.
- `NavLinks variant="bottom"` renders **icons only, no text**. Measured before the change: the six 12px labels had **0.0px of margin at every width** and were genuinely truncated at 320px ("Finances" wanted 59px in a 53.3px slot), because `truncate` was already sitting on the links. The names survive in three other places, so nothing is lost: `aria-label` on each link, `aria-current="page"` on the active one, and the desktop sidebar, which still renders `item.label` as text. Slots stay at 50px tall so the bar grew by only 2px (48 → 50).
- The nav icons are hand-written SVGs in `IconButton.tsx` next to the existing ones, and `NAV` in `app/lib/nav.ts` carries the `icon` key — it is the single source read by the sidebar, the bottom bar *and* `BurgerMenu`, so a new entry needs its label; the icon is optional and an entry without one **falls back to a text label** rather than rendering an empty slot.
- `BurgerMenu` takes a `size` prop (`"sm"` default, `"md"`) so its `MoreIcon` (and tap target) can be enlarged for one call site — `app/components/MobileHeader.tsx` passes `size="md"` — without touching the other (`NavLinks`' desktop sidebar), since both share the same component.

## Serialization & dates (easy to get wrong)

- **Prisma `Decimal` fields reach the client as JSON *strings*** (`Transaction.amount`, `Budget.amount`, `Reminder.estimatedAmount`, `Recipe.estimatedCost`) because `Decimal#toJSON` returns a string. Routes just `NextResponse.json(prismaResult)`. So every read must be wrapped: `Number(t.amount)`, `Number(x).toLocaleString("fr-FR")`, and form seeding uses `String(Number(tx.amount))`. There is **no** `Prisma.Decimal` import and no `.toFixed()` anywhere — formatting is always `.toLocaleString("fr-FR")`.
- Client → API: zod schemas expect `z.number()`, so form strings are parsed with `parseFloat(String(v).replace(",", "."))` and nulled when `!isNaN(v) && v > 0`.
- Import dayjs **only** from `@/app/lib/dayjs` (it extends `isoWeek` + `utc` and sets locale `fr`). Four files still import raw `"dayjs"` — `app/api/push/send`, `app/api/push/digest`, `app/api/schedule`, `app/api/stats` — so they get `fr` but **not** `isoWeek`/`utc`; adding an isoWeek or `dayjs.utc` call there will throw. Every file using `dayjs.utc` imports the aliased module, so never mix a raw and an aliased import in the same file.
- **Date-only calendar fields are stored at a fixed UTC instant and must be read with `dayjs.utc()`.** Five fields: `Transaction.date` (written `T00:00:00.000Z`), `Budget.periodStart` (`T00:00:00.000Z`), `Budget.periodEnd` (`T23:59:59.000Z`), `Reminder.recurrenceEndDate` (`T23:59:59.000Z`), and `ScheduleEvent.specificDate` (`T${startTime}:00.000Z`). Reading them with plain `dayjs()` renders in the browser's zone, so in a negative offset (`America/New_York`, `Pacific/Midway`) the day shifts **back one** and the form re-seeds on the wrong date — every save then moves the stored value back a day. `dayjs.utc(x).format("YYYY-MM-DD")` returns the intended calendar day in every zone from UTC-11 to UTC+14.
- **Do not mix a UTC calendar field with a local `dayjs()` in the same comparison.** `isSame(x, unit)` resolves in the first operand's zone, so `dayjs.utc(d).isSame(dayjs(), "month")` is ambiguous. Compare formatted strings instead: `dayjs.utc(t.date).format("YYYY-MM") === dayjs().format("YYYY-MM")`, where the right-hand side stays **local** ("today"/"this month" is the user's local notion).
- `Reminder.dueDate` is the opposite case: a genuine **instant** from a `datetime-local` input, always read/compared in local time. Do not switch it to `dayjs.utc()`. `nextDue()` in `app/lib/recurrence.ts` therefore returns a *local* `Dayjs`, which is why the recurrence cut-off compares `nd.format("YYYY-MM-DD") <= dayjs.utc(r.recurrenceEndDate).format("YYYY-MM-DD")` as strings — comparing instants there let a positive-offset zone run one day past the configured end.
- There is no `TZ` and no tzdata in the image, so the server renders in UTC. `dayjs(...).format("HH:mm")` on an instant shifts by the browser's offset. `app/api/stats` computes `startOf`/`endOf("month")` with `dayjs()` server-side (UTC) while `app/(dashboard)/page.tsx` compares against the client's local month — they can disagree in the first/last hour of a month boundary.
- Reminder due date uses a **single `datetime-local` input** (`app/components/RemindersView.tsx`). It was split into date+time and then explicitly reverted twice — do not re-split. `ScheduleView` legitimately uses `type="date"` + two `type="time"` inputs because `ScheduleEvent.startTime`/`endTime` are `"HH:mm"` **strings** in the DB, regex-validated in zod.
- `app/lib/week.ts` indexes Monday-first arrays with `isoWeekday()` (1=Mon..7=Sun), while `app/(dashboard)/page.tsx` has a hand-rolled **Sunday-first** `DOW` array indexed by `dayjs().day()`. They coexist and disagree — don't mix them.

## Validation

zod (v4) is used on **POST of collection routes** (`reminders`, `notes`, `budgets`, `categories`, `transactions`, `schedule`, `recipes`, `recipes/[id]`), always as `safeParse` → `return NextResponse.json({ error: parsed.error.flatten() }, { status: 400 })`. Enums are hand-written string unions mirroring the Prisma enums, not `z.enum(...)`; dates are `z.string().datetime()` converted with `new Date(...)`; foreign-key ownership is checked *after* zod with its own 400.

**All seven `PUT` handlers on `[id]` routes now validate**, via a `xxxPatchSchema` exported by the collection route and imported by `[id]/route.ts`. Each collection route therefore holds a `xxxShape` const, a `xxxSchema = z.object(xxxShape)` for POST, and the patch variant. Three non-obvious traps, all verified against zod 4.4.3:

- `z.object` **strips** unknown keys, which is what closes the mass-assignment hole — always pass `parsed.data` to Prisma, never `body`. A raw `data: body` lets a client set `userId`.
- **`.partial()` does not cancel a field's `.default()`.** `z.object(shape).partial()` on a shape containing `currency: z.string().default("XOF")` re-injects `"XOF"` on every update that omits it. Override the default with `.optional()` *before* `.partial()` (as done for `transactionShape`, `budgetShape`, `reminderShape`).
- `.partial()` **throws** on a schema carrying `.refine()` ("cannot be used on object schemas containing refinements"), so `scheduleEventShape` is kept un-refined and refined separately for POST only. A partial update must not re-assert the "either dayOfWeek or specificDate" rule — the stored row already satisfies it.

Reusing a POST schema for PATCH also breaks nested objects: the POST `items` element is only `{ label }`, so `checked`/`id` would be stripped and the checkbox state silently lost. `reminderPatchSchema` declares its own richer `items` element for that reason. It also adds `status: z.enum(["PENDING","DONE"])` — note `OVERDUE` is derived and must stay out of the API. `recipes/[id]` reuses `recipeSchema` directly since PUT there is a full replace.

`endAfterStart()` (`app/api/schedule/route.ts`) is the single "end > start" rule, shared by the POST `.refine()` and by the PUT handler — a partial update cannot re-check the pair it did not receive, so the PUT compares against `existing.startTime`. This matters because `findOverlaps` tests `cStart < eEnd && eStart < cEnd`: a stored inverted interval makes `cEnd < cStart`, so the condition is **never** true and the event silently escapes conflict detection. `ScheduleView` also guards it client-side, so the user gets an inline message instead of a round-trip.

Clients only surface `error.formErrors` (`data?.error?.formErrors?.join(", ")`); `fieldErrors` are parsed and then dropped, so per-field messages are invisible in the UI.

## Styling (Tailwind v4, CSS-first)

There is **no `tailwind.config.*`**. `app/globals.css` does `@import "tailwindcss"` then defines the whole palette in `@theme` (`ink`, `surface`, `surface-raised`, `border-log`, `parchment`, `muted`, `brass`, `amber`, `teal-log`, `rust`) — add a colour there. Fonts map to non-obvious utilities: `font-display` (Fraunces), **`font-mono-log`** (IBM Plex Mono, *not* `font-mono`), `font-sans` (Inter).

Hand-written classes in `globals.css` that you should reuse: `.mobile-page-header` / `.mobile-page-root--*` (the fixed-header + offset system, now emitted only via `PageLayout`), `.pwa-sheet-overlay` / `.pwa-sheet` (all modals; `z-index: 60` is set globally there), `.pwa-bottom-nav`, `.initial-loading` (+ `app/components/InitialLoading.tsx`). Offsets derive from the CSS vars `--mobile-header-height` / `--mobile-page-title-height` / `--mobile-page-subheader-height`; the desktop breakpoint is hardcoded at `min-width: 768px` with `left: 224px` to clear the `md:w-56` sidebar — change one, change the other.

**The `--filters`/`--responsive-tools` padding-top formulas double as a tape measure for the header's actual rendered height — they drift the moment the header's content grows.** `PageLayout` adds `mt-2` (`controls`, used by `RemindersView`) / `mt-2 md:mt-0` (`actions` on `variant="responsive-tools"`, used by `ScheduleView`) so the title row isn't flush against the row below it on mobile. Every `--mobile-page-root--*` padding-top in `globals.css` bakes in a `+0.5rem`/`+0.75rem` literal to match. If you touch the header's JSX (add a row, change a gap), recompute these by hand — there's no `ResizeObserver` tying them together, so a mismatch doesn't error, it just reopens the "content starts under/over the fixed header" bug this was fixed for twice already.

**`type="date"` inputs need `min-w-0` even outside a flex row.** Some mobile browsers give the native date control an intrinsic minimum width wide enough to overflow a `w-full` container; the `flex-1` pair in `BudgetsView`'s Début/Fin additionally needs `min-w-0` on the wrapper `<div>` too, mirroring `ScheduleView`'s `type="time"` pair — a `flex` item's default `min-width: auto` ignores `width:100%` on the child and sizes to content instead, which is what actually overflowed there.

**Stacking context trap:** the hand-written classes come *after* `@import "tailwindcss"` in `globals.css`, so at equal specificity they beat a Tailwind utility. A `z-[70]` on a `.pwa-sheet-overlay` is silently ignored — the global `z-index: 60` wins. `ConfirmDialog` (the delete-confirmation nested inside an edit sheet) therefore sets `style={{ zIndex: 70 }}` inline, which cannot lose. Use the same trick for any overlay-on-overlay.

**Destructive actions are confirmed** via `app/components/ConfirmDialog.tsx`, not `window.confirm` (which SettingsView still uses in 2 places). The pattern in the six edit modals is a two-state `remove`: the first click does `if (!confirming) return setConfirming(true)`, the second `setConfirming(false)` and proceeds. Note this needs the modal's `return (...)` wrapped in a `<>...</>` fragment, because the dialog is a **sibling** of `.pwa-sheet-overlay`, not a child.

## Push, recurrence, and the service worker

- Two crons hit protected endpoints with `Bearer $CRON_SECRET`: `*/10 * * * *` → `POST /api/push/send` (REALTIME reminders + budget alerts) and `7 0 * * *` → `POST /api/push/digest` (MORNING reminders).
- `app/lib/recurrence.ts` is the reminder brain and is **client-shared** — the same functions drive UI state and cron alerts. `derivedStatus()` returns `OVERDUE` as a *derived, non-persisted* value (only `PENDING`/`DONE` exist in the enum), so `where: { status: "OVERDUE" }` in a Prisma query is a bug. `stagesFor()` returns `[70,90,100]` vs `[50,80,100]` based on a 90-day window; `windowStart()` anchors the push window and differs for recurring vs one-shot. `dayjs.add(1,"month")` clamps/overflows end-of-month dates (Jan 31 → Mar 3).
- Reminder dedup: `sentStages` is an **Int bitmask** (bits 0/1/2). `PUT /api/reminders/[id]` resets `sentStages = 0` whenever `dueDate` is present in the body — which also re-arms pushes on an unrelated re-save.
- `/api/push/send`'s reminder query filters `dueDate` by an upper bound only (`to`, 365 days ahead) plus `sentStages: { lt: 7 }`, **never a lower bound**. An earlier version also had `dueDate: { gte: now - 1min }`: since the cron runs every 10 min, that gate excluded any reminder more than 1 min overdue from the query entirely — the 100%-stage push (which fires exactly *at* `dueDate`) only landed if a tick happened to hit within a 1-minute window, roughly 1 run in 10, and was otherwise lost **permanently** (the row never matched the `where` again). `sentStages < 7` is what now bounds the query instead, so a reminder stays visible to every cron tick until all 3 stages are actually marked sent.
- In that same loop, stage bits are only persisted into `sentStages` when `sendPushToMany`'s returned count is `> 0` — i.e. at least one subscription actually received the push. Previously the bits were written unconditionally once `highestUnset >= 0`, so a user with zero push subscriptions (never opted in) or a transient webpush failure got that stage permanently marked "sent" with nothing ever delivered, and no retry on a later cron run. Don't go back to unconditionally marking bits on `passed` — it silently burns notifications.
- `PUT /api/reminders/[id]` syncs `items` as a **diff inside `prisma.$transaction([...])`**, not `deleteMany` + `createMany`: kept items keep their `id` (so `/items/[itemId]` toggles aren't orphaned by a re-save) and the whole sync is atomic. An `id` that doesn't belong to this reminder is **not** an error — it falls through to `create`, which is what stops a forged id from writing into another user's item. Renumbering `order` comes free from indexing the submitted array.
- Budgets alert once per period via `alertLevel` + `alertSentAt` (80/95/100 %), reset when `alertSentAt` predates the period start.
- `app/lib/push.ts` calls `webpush.setVapidDetails()` **at module scope**, so importing it without `VAPID_*` set throws. `sendPush` auto-deletes subscriptions on 404/410 then rethrows; `sendPushToMany` swallows per-subscription errors and returns a count (the crons only report counts). It imports `prisma`, so it is server-only.
- `public/sw.js` is hand-written (no `next-pwa`). **It caches `GET /api/*`** (network-first, `caches.put` on every ok response) and precaches `/` as the navigation fallback, so adding/renaming a GET endpoint surfaces as stale data in the installed PWA. Bump `CACHE_NAME` (`rapply-cache-v3`) when you change caching behaviour. Non-GET methods and `/api/auth*`, `/api/push/send`, `/api/push/digest` bypass the SW entirely. `notificationclick` only focuses an existing window or opens `/` — no deep links.
- **Every dashboard route plus `/recettes`/`/parametres` is precached** on `install` (`PRECACHE_ROUTES` in `sw.js`), one `cache.add()` per URL with its own `.catch(() => {})` — not `cache.addAll()` — so one route failing to fetch doesn't abort the whole SW install. This only works because `ServiceWorkerRegistrar` only registers in production from inside `(dashboard)/layout.tsx`, i.e. the user is already authenticated by the time `install` fires, so these same-origin fetches carry the session cookie and cache the real authenticated page, not a login redirect. `/offline` and the truly static assets (`/`, manifest, icons) are in the separate `PRECACHE_STATIC` list, which *does* use `cache.addAll()` (all-or-nothing) because none of them can plausibly fail.
- The navigate-mode fetch handler's cache-miss fallback is `/offline` (`app/offline/page.tsx`, a static client page, no data, no `PageLayout`), **not `/`**. Falling back to `/` used to silently substitute the dashboard home's cached HTML under whatever URL the user actually requested (e.g. visiting `/schedule` offline for the first time rendered the dashboard, address bar still saying `/schedule`) — confusing, wrong-content-under-the-URL behaviour. Don't revert that fallback target.
- `app/(dashboard)/error.tsx`, `app/recettes/error.tsx`, `app/parametres/error.tsx` (plus a root `app/global-error.tsx`, which per Next's convention renders its own `<html>/<body>` and can't use Tailwind classes from `globals.css` since it replaces the whole root layout — hence the inline `style` objects) catch a `page.tsx` throwing — e.g. `serverFetch` rejecting because the device is offline and the SSR request never reaches the server. Before these existed there was **no `error.tsx`/`global-error.tsx` anywhere**, so that case fell through to Next's generic default error page instead of anything app-authored. `reminders/page.tsx` and `parametres/page.tsx` still don't wrap their `serverFetch` calls in try/catch (unlike the dashboard home's `safe()` helper) — that's intentional now: the error boundary turns the throw into a "Réessaie" card instead of a silently-wrong zeroed-out page.
- `ServiceWorkerRegistrar` is mounted from `app/(dashboard)/layout.tsx` and **no-ops unless `NODE_ENV === "production"`**; since `/recettes` and `/parametres` sit outside that group they never register the SW at all. `PushSubscribeButton` is rendered by `SettingsView` (Paramètres), **not** the dashboard, and registers `/sw.js` itself before subscribing because the registrar is dev-inert. It posts to `/api/push/subscribe`, which deliberately stays behind the proxy so `x-user-id` is available.

## Recipes

Recipes are a self-contained feature: `app/recettes/page.tsx`, `app/components/RecipesView.tsx`, `app/api/recipes/**` (including `shopping-list`). It is the only place with zod on an `[id]` route. Note `Recipe.estimatedCost` (not `estimatedAmount`) is the Decimal field, and a recipe can be linked 1:1 to a `Note` via `noteId`.

`app/api/export/route.ts` is a **backup, so it must cover every entity type** — it is not a selective report. It exports 8 top-level keys: `user`, `categories`, `reminders`, `notes`, `transactions`, `budgets`, `scheduleEvents`, `recipes`. Child rows are **nested** under their parent, not exported as separate top-level collections: `ReminderItem` via `reminders.include.items`, and `Ingredient`/`Step`/`Accessory` via `recipes.include`. `ReminderItem` and the three recipe children carry **no `userId`**, so they can only be scoped through `reminderId`/`recipeId` — a flat `findMany({ where: { userId } })` on them is impossible. When you add a model to `prisma/schema.prisma`, add it here too, and bump `version` only for a breaking shape change. There is currently no import/restore endpoint.

## Deploy

- `next.config.ts` uses `output: 'standalone'` + global security headers (HSTS, `X-Frame-Options: DENY`, …). Don't add per-route headers there without checking this catch-all `/(.*)` block.
- The Dockerfile is 3-stage: `pnpm install --frozen-lockfile` → `npx prisma generate` **then** `pnpm build` → non-root `nextjs` runner on `node server.js` with `.next/standalone`.
- All 7 secrets (`DATABASE_URL`, `JWT_SECRET`, `CRON_*`, `VAPID_*`, `NEXT_PUBLIC_*`) are passed as **build ARGs** and declared in **both** the Dockerfile and both blocks of `docker-compose.yml` (`build.args` and `environment`). A new `NEXT_PUBLIC_*` var must be added in all three places, or it is `undefined` at build time.
- **No `prisma migrate deploy` runs in the image** — schema changes must be applied out-of-band.
- `docker-compose.yml` joins the external `traefik-network` and routes `Host(\`${DOMAIN:-rapply.voisilab.app}\`)`; there is no DB service (external Postgres via `DATABASE_URL`).
